## MODIFIED Requirements

### Requirement: Suggested Replies Configuration & Lenient Hot-Reload
The system SHALL provide a `[suggested_replies]` configuration section (`SuggestedRepliesConfig`) with `enabled` (bool, default `true`), `jev_provider` (string, default `"auto"`, supporting `"auto"`, `"laya"`, `"openjev"`, `"typesafe"`, `"openrouter"`, `"aimlapi"`, and `"jcode"`), `use_open_gf` (bool, default `false`), `max_secondary_suggestions` (usize, default `5`, clamped `1..=5`), `confidence_threshold` (f32, default `0.55`, clamped `0.0..=1.0`), `show_confidence` (bool, default `true`), `custom_prompts` (Vec<String>, default empty, aliases `custom_questions`, `custom_candidates`, `pinned_prompts`), `enable_full_auto_explorer` (bool, default `false`), and `six_lens_auto_review` (bool, default `false`).

#### Scenario: Lenient config parsing and environment fingerprint tracking
- **WHEN** `config.toml` or `JCODE_*` environment variables (including `JCODE_SUGGESTED_REPLIES_SHOW_CONFIDENCE` and `JCODE_SUGGESTED_REPLIES_CUSTOM_PROMPTS`) specify `[suggested_replies]` values (including out-of-range integers or floats)
- **THEN** `SuggestedRepliesConfig` clamps `max_secondary_suggestions` into `1..=5` and `confidence_threshold` into `0.0..=1.0`, sanitizes non-empty `custom_prompts` entries without failing `Config::load_from_file_strict()`, and `CONFIG_ENV_KEYS` tracks every environment variable override for hot-reload.

### Requirement: Two-Stage Macro/Micro Branching with OpenJev / Laya SystemOne and OpenGF
The system SHALL execute a two-stage cascade at turn completion using a structured `SuggestedRepliesContext` (`last_user_message`, `last_assistant_message`, `assistant_options`, `pending_todos`, `recent_turns`, `language_is_cyrillic`). Both Iteration 1 and Iteration 2 SHALL pass a structured JSON `state` object to SystemOne (`build_structured_systemone_state`). Iteration 1 determines the macro conversation branch (via SystemOne `choice`/`noul` against the structured context `state` when `use_open_gf = false`, or via OpenGF `Sidecar` / configured `[providers.*]` / external OAuth fallback routes with `"store": false` when `use_open_gf = true`), and Iteration 2 merges any configured `custom_prompts` (`custom_questions`) into the candidate pool (deduplicated case-insensitively, up to 12 total candidates) and scores all candidate actions against `{ branch, last_user_message, last_assistant_message, assistant_options, pending_todos, candidates: { cand_0..cand_N } }` via the configured SystemOne provider (`JevProvider::Laya` over loopback or trusted Tailscale/private LAN HTTP, or `JevProvider::OpenJev` / `TypeSafe` / `OpenRouter` / `Aimlapi` / `Jcode`). When the active SystemOne provider supports `choice` questions and at least two candidates are present (`candidates.len() >= 2`), Iteration 2 SHALL submit both a comparative `best_candidate` (`type: "choice"` over `cand_0..cand_N`, capped so total questions `<= 24` to respect `MAX_QUESTIONS`) and individual `cand_0..cand_N` (`type: "noul"`) questions in a single batch request, combining `noul`, `choice.probabilities`, and rank prior in `calibrate_micro_score_with_choice` (falling back to `noul`-only when `candidates.len() == 1` or when the provider only accepts `noul`). Existing public entry points (`evaluate_cascade`, `score_locally_from_context`, `build_micro_scoring_noul_questions`) SHALL remain backward-compatible.

#### Scenario: Default Action promotion and secondary suggestions distribution
- **WHEN** candidate actions (including any configured `custom_prompts`) are scored (via joint `choice + noul` SystemOne evaluation or deterministic local scoring) and sorted by `confidence` descending
- **THEN** if the top candidate has `confidence >= confidence_threshold`, it is assigned to `defaultAction` and up to `max_secondary_suggestions` remaining candidates are placed in `secondarySuggestions`; otherwise `defaultAction` is `None` and up to `max_secondary_suggestions` candidates are placed in `secondarySuggestions`.

#### Scenario: Structured JSON state and joint choice+noul micro-scoring batch
- **WHEN** Iteration 2 evaluates `>= 2` candidate replies on a provider that supports `choice` (`Laya`, `OpenJev`, `TypeSafe`, `OpenRouter`, `Aimlapi`)
- **THEN** the request `state` is a structured JSON object containing `candidates.cand_0..cand_N` (plus conversation and `pending_todos` context), the `questions` map contains `best_candidate` (`type: "choice"`) alongside `cand_0..cand_N` (`type: "noul"`) within the provider's question limit, and `calibrate_micro_score_with_choice` fuses the `noul` probability, `best_candidate` softmax probability, and rank prior; if only 1 candidate is present or the provider is `Jcode` (`noul`-only), Iteration 2 omits `best_candidate` and evaluates `cand_0` via `noul`.

## ADDED Requirements

### Requirement: Assistant Question Option Extraction, User Constant Questions, and Language-Aware Dynamic Candidate Pool
The system SHALL inspect `last_assistant_message` for explicit questions or numbered/bulleted options, detect the user's conversation language (Cyrillic/Russian vs English), and merge any user-configured `custom_prompts` (`custom_questions`) into the candidate pool so both OpenGF and local fallback evaluations score the user's constant questions alongside context-relevant replies in the user's language.

#### Scenario: Russian conversation, assistant option list, and custom_prompts
- **WHEN** `custom_prompts` are configured in `[suggested_replies]` or `use_open_gf = false` and the recent user turn is in Russian or the assistant message ends with numbered/bulleted options or pending `todo` items
- **THEN** the candidate pool includes the user's `custom_prompts` alongside direct responses to the assistant's options, the next pending `todo` item, and Russian-localized workflow actions, scoring and ranking all of them together.
